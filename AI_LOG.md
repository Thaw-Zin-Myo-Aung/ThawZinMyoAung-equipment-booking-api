- **Wrong claim in a draft review:** the AI's first draft of Quality Gate finding #5 said v1 PATCH did not validate the merged start/end. - **Date parsing:** I checked how JavaScript's `Date` parses edge cases in Node before relying on it. `2026-02-30` became March 2, and `10/20/2026` was parsed in local time (+07). This is why strict validation was added instead of trusting `new Date()`.

## In my own words

- Why 404 for an unknown equipmentId: The request to `POST /bookings` is well-formed. The JSON is valid, every field has the right type, and the times are valid. The only problem is that the equipment it refers to does not exist, so I report that missing resource with 404 and a clear message (`Equipment 'eq-999' does not exist`). I keep 400 for data that is wrong by itself, such as a missing field, a wrong type, a bad date, or a start time after the end time. The `/bookings` route itself exists. The 404 is about the referenced equipment, not the URL. 400 would also be defensible, but I chose 404 so the client can tell "fix your data" (400) apart from "that equipment doesn't exist" (404).
- How the overlap check works (create and update): The overlap check works by querying the database for any existing bookings that have a time range that intersects with the requested booking's time range. When creating a new booking, the system checks if there are any existing bookings for the same equipmentId that have a start time before the requested end time and an end time after the requested start time. If such a booking exists, it indicates an overlap, and the request is rejected with an appropriate error message. For updates, the same logic applies, but it also excludes the current booking being updated from the overlap check to avoid false positives.
- AI output that turned out to be wrong, and how it was corrected and checked:
  - **Test script false pass.** The first test script only compared status codes, so v1's plain-text 404 for an unknown route was reported as PASS even though it broke the JSON-error rule. This was caught during the review, and a check was added that every error body is `{"error": "..."}`. I confirmed the re-run on v1 then showed 4 failures instead of 3.
  - **Wrong claim in Quality Gate finding #5.** The first draft said v1's PATCH did not validate the merged start/end. Comparing it with the v1 code (`git show 04dc9d3:src/index.ts`) showed that it did. The finding was rewritten to describe the real v1 PATCH problems: no type checks, `null` silently ignored, and an empty PATCH accepted. I checked these against v2 with curl (all now return 400).
  - **Trusting `new Date()` in v1.** The v1 code used `new Date()` alone to validate dates. Testing edge cases in Node showed that `2026-02-30` silently becomes 2 March and `10/20/2026` is parsed in local time (+07). v2 therefore uses a strict ISO-8601 check plus a calendar-day check. I confirmed both cases now return 400 (E8 and E11 in `evidence/after_v2.txt`).
- What I decided myself: keep 404 for an unknown equipmentId, keep back-to-back bookings allowed, do not add CORS because I test with Postman and curl rather than a browser, and run the server and all Postman tests and screenshots myself.
